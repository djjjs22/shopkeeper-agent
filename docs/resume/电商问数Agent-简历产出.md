## 一、项目定位

**项目名**:Shopkeeper Agent —— 自然语言驱动的电商问数系统

**一句话概括**:  
业务方用大白话提问(比如"今年第一季度各大区销售额"),系统自动从元数据知识库检索表/字段/指标,生成 SQL,过三层安全校验后执行查询;失败自动修正、反思重试,平均 3 秒出结果。覆盖了从 LangGraph 图编排、SQL 安全、到记忆体系和自学习数据飞轮的完整 AI 落地链路。

**LangGraph 编排的角色**:  
LangGraph 是 LangChain 出的"图状态机"框架,核心是把 AI 工作流拆成节点 + 条件边。本项目用它搭了两层图:底层 17 节点单链路图(分类 → 改写 → 关键词抽取 → 三路召回 → 合并 → 生成 SQL → 校验 → 修正 → 执行),顶层 4 节点多智能体图(规划 → 并行执行 → 聚合 → 评审)。LangGraph 让每一步的输入输出都进全局 state,出错自动重试、闲聊自动旁路、SQL 走安全闸门,这是普通 if-else 撑不住的有向图能力。

**技术栈**:  
LangGraph 17 节点有向图 · FastAPI · React · Qdrant · Elasticsearch + IK 分词 · MySQL · Redis · LangSmith · Jieba · LLM Profile Registry(cheap / strong 双槽位)

**需求背景**:  
电商运营日常问数全靠分析师写 SQL,流程是业务提需求 → 分析师接单 → 写 SQL → 排队执行,一个简单问题平均要走半天。LLM 套壳能直接生成 SQL,但有两个真问题:一是 LLM 凭记忆猜表结构,字段名错、关联关系错,准确率不到 30%;二是 LLM 生成的 SQL 不能直接执行,拼错、注入、误删表都是隐患。

这个项目要做的核心是:在 LLM 之外搭一套**有向图编排 + 多路召回 + 安全校验 + 反思回路 + 记忆体系 + 数据飞轮**,让系统能"自己变聪明",而不是靠每次手动调提示词;让非技术业务方说一句人话,3 秒拿到一份可信、可执行、可上生产的结果。

## 二、核心亮点(5 条,STAR 法则)

### 亮点 1 · 17 节点 LangGraph 有向图 + 三路召回(STAR)

**S**:  
电商表 60+ 字段,业务方提问里的 `GMV / 华东 / 动销率` 分别对应不同列(指标名 / 枚举值 / 抽象概念),单 LLM 直觉猜,召回率不到 40%。

**T**:  
搭一套召回机制,让业务口语 → 表/字段这一步稳到能上生产,不需要人工辅助。

**A**:  
搭了一条 17 节点的有向图,核心是**三路召回 + 上下文拼接**:

- 字段召回走 Qdrant 向量(用 bge-large-zh-v1.5 编码),`销售额` 跟 `order_amount` 语义命中
- 枚举值召回走 Elasticsearch + IK 分词,`华东/华南` 精确匹配,避开向量太近混淆的问题
- 指标召回也走 Qdrant,`GMV` 这种抽象概念向量能搜到

三路结果合并 + filter,再补时间、库元信息,才让 LLM 推理。

**R**:  
端到端问数从半天分析师排队压到**平均 3 秒出结果**;三路召回互补,Qdrant 管语义、ES 管精确,业务术语召回率从 < 40% 升到能上生产的水平。

---

### 亮点 2 · LLM 输出不可信,三层安全防火墙 + 自动修正回路(STAR)

**S**:  
LLM 生成的 SQL 是幻觉产物,直接执行轻则报错、重则误删表。任何 LLM 直接连数据库的方案都不能上生产。

**T**:  
SQL 执行前过三层校验,任意一层失败,要么拦截,要么回 LLM 修正,绝不让脏 SQL 落到 MySQL。

**A**:  
做了 `SQLSafetyValidator`,5 道闸门:

1. **关键字黑名单**:`DROP / DELETE / UPDATE / INSERT / ALTER` 等写操作直接拦
2. **只读白名单**:只允许 `SELECT / WITH` 开头
3. **SQL 注入检测**:`UNION SELECT / OR '1'='1' / --` 注释截断
4. **EXPLAIN 预演**:不实际执行,MySQL 只解析语法
5. **自动修正回路**:语法错 → 错误信息 + 原 SQL 回传 LLM 修正 → 再 EXPLAIN

字符串预处理先移除引号内容再匹配关键字,避免 `WHERE name='DROP ME'` 这种被误杀。

**R**:  
校验顺序、注入优先于表名白名单,错误分类不串;多层校验 + EXPLAIN 预演,LLM 出错也不会污染数据库;单测 41 个用例覆盖关键字 / 白名单 / 注入 / 防误杀。

---

### 亮点 3 · 多智能体模式:并行拆子问题 + 反思回路(STAR)

**S**:  
单条链路只能答一个问题,但业务方常问"今年第一季度各大区销售额 + 同比 + 环比"——这是 3 件事。多子问题串行跑慢,合并靠 LLM 拼凑,质量也说不清。

**T**:  
当一个问题能拆成多个子问题时,让多个子问题并行跑,然后聚合;如果聚合结果质量不够,触发反思重做。

**A**:  
用 LangGraph 搭了顶层图接子图,分四步走:

1. 规划节点把问题拆成子问题(单子问题直接走老链路不调 LLM,快)
2. 多子问题时用 LangGraph 并行接口同时跑子图
3. 聚合节点合并子问题结果
4. 评审节点打分,低于 0.7 触发反思回路,最多重做 2 次防止死循环

接口默认走单链路 3 秒出结果,前端传参 opt-in 开启多智能体模式。

**R**:  
复杂多子问题从串行 + LLM 拼升级到并行 + 评分 + 反思,质量有量化指标(评审员评分)兜底,反思有 2 次重做上限防止卡死。

### 亮点 4 · Memory 三层 + 数据飞轮:让系统自己变聪明(STAR)

**S**:  
传统 LLM 应用靠每次手动调 prompt,系统用得越久反而越难维护。要让 Agent 真正"自己变聪明",得有三层长期记忆,以及一个能持续反哺的飞轮闭环。

**T**:  
搭一套记忆体系 + 数据飞轮,让用户每次查询的"成功 / 失败"信号都沉淀下来,反哺召回与生成,系统越用越好,而不是每次靠人重写提示词。

**A**:  
记忆体系分三层:

- **程序性记忆**:历史成功 SQL 抽成 59 条模板,召回时作为示例喂给 LLM;同时建 MySQL 全文索引 + Qdrant 向量双路检索,人工标注来源置信度 1.0,线上来源从 0.5 随被引用次数增长
- **语义记忆**:从用户提问自动抽偏好(默认维度、常用术语),置信度从 0.5 起步,3 次连续命中升到 0.9 才注入提示词,矛盾反馈自动重置
- **情景记忆**:会话超过 5 轮自动触发摘要,保留近 4 条原文 + 1 条摘要,失败时保留原始历史不丢数据

数据飞轮:

- 4 处自动埋点(SQL 校验失败、LLM 修正放弃、评审低分、用户点 👎)→ 归集到失败案例表
- 成功的查询落到查询日志表
- 人工 review 失败案例进测试集 → 回归 CI 阻断合并(准确率下降 > 2% 直接 fail)
- 每日 03:00 跑自动衰减,污染的模板 / 偏好自动降权或删除

**R**:  
系统能"自己变聪明"——用户连续用 3 次默认"按地区分",以后自动按地区;失败案例积累到测试集反哺提示词;端到端评测从 0 跑到 86.7%,降到 80% 直接 CI 红。这是把 LLM 套壳变成可持续 AI 系统的关键。

---

### 亮点 5 · 多轮会话架构:内存兜底 + Redis Pipeline + 7 天冷热分层(STAR)

**S**:  
业务方要追问(上句问 `2025 华东 GMV`,下句问 `那华南呢`),会话历史必须可持久、可降级、可归档。早期用 Python 内存 dict 撑过 demo 期,但有 3 个生产级问题:重启数据丢失、多机不共享、过期不清理;同时单次 LLM 调用上下文撑爆要解决——历史太长会撞 max_tokens,太短又断上下文。

**T**:  
搭一套会话存储架构,既要让追问连续性稳(重启不丢),又要给 LLM 喂的 prompt 上下文可控不撑爆;Redis 挂了不能挂服务。

**A**:  
搭了多层会话架构,关键设计 5 个:

- **内存兜底**:Python dict + 线程锁,长度截断 500 字符 + 数量截断 10 条,Redis 不可用时静默降级,接口不挂
- **三阶段写入模式**:`memory_only` / `dual_write` / `redis_primary`,通过环境变量切换,平滑迁移不丢数据
- **Redis 管道原子操作**:三个命令(追加、保留最后 10 条、设 24 小时过期)打包一次网络往返,中间断网全部回滚
- **降级策略**:连续失败 3 次才标记 Redis 不可用(防网络抖动误降级),可用时自动重置
- **7 天冷热分层**:7 天前的会话从 Redis 归档到 MySQL 冷库,增量遍历避免阻塞(避免生产事故),定时任务 02:00 自动跑
- **接口与实现分离**:会话存储的 3 个函数(`get_history` / `add_message` / `clear_history`)签名稳定,内存 / Redis 实现可换,业务调用方零改动

**R**:  
接口和实现分离的红利——从纯内存升级到 Redis 主,业务调用方一行代码不用改;Redis 挂了自动降级,服务可用性不受影响;7 天冷热分层让长期会话不丢,Redis 内存只保留近期热数据,运维成本可控。这是把 demo 状态推进到生产可用的关键基础。

### Shopkeeper Agent

**技术栈**:LangGraph · FastAPI · React · Qdrant · Elasticsearch · MySQL · Redis · LangSmith

**项目描述：**&#x7535;商运营问数走分析师排队流程,简单问题平均要走半天;LLM 套壳能直接生成 SQL,但 LLM 凭记忆猜表,无法直接执行。为解决真实问题,设计一个由 agent 驱动的自然语言问数系统。

**项目细节**:

- **LangGraph + 三路召回**:17 节点有向图把"问问题"拆成多步,业务方口语按指标名 / 枚举值 / 抽象概念三路互补检索;**端到端 86.7% SQL 准确率(15 条金标准评测),3 秒出结果**。
- **SQL 五道安全闸门**:LLM 生成的 SQL 进数据库前必过 5 道关(拦截危险关键字 / 限查询 / 注入检测 / 预演校验 / 失败回 LLM 修正),按风险等级排序;**41 个单测覆盖,误删表 / 注入风险归零**。
- **多智能体并行 + 反思回路**:把"各地区销售额 + 同比 + 环比"这种 3 件事的问题并行执行(同时查 3 个子 SQL),评审员 < 0.7 触发反思、最多 1 次防卡死;**派生指标(同比、环比)等刁难用例能跑通**。
- **三层记忆 + 数据飞轮**:59 条历史成功 SQL 抽成模板作为示例喂 LLM + 自动学用户偏好(3 次命中才信) + 多轮 5 轮自动摘要;失败 case 4 处埋点 → 人工修正进金标准集 → 提 PR 跑 CI 退化 2% 阻断合并;**基线 86.7%、CI 退化 2% 自动阻断合并**。
- **全链路观测**:每个节点用装饰器自动打点结构化日志(每节点耗时多少毫秒 + 状态),LLM 调用聚合 token 消耗 / 调用次数 / 错误率(按强弱模型分别统计),集成 LangSmith 追踪所有 LLM 调用(17 节点主图 + 多智能体子图全覆盖);**3 秒可拆解到每节点多少毫秒,LLM 成本按模型看**。

1. **数据漂移问题：** 自定义 Flume 的 Kafka Source 的 Intercepter，将 event 中 header 的时间戳字段替换成 body 中的日志生成时间，HDFS Sink 会基于 event 中的时间戳落盘；
2. **Flume 将数据同步至 HDFS 的小文件问题：** 配置 `hdfs.rollInterval`、`hdfs.rollSize`、`hdfs.rollCount` 限制新文件的生成。
