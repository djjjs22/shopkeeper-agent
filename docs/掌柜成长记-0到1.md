## 阶段 0:MVP 期(2026-06 月底)

### 当时状态
- 项目是"套壳 LLM",让 GPT 直接读 schema 写 SQL
- 没有任何安全校验
- 单 LLM 调用,无 RAG

### 主要问题
- ❌ LLM 写 SQL 经常拼错字段名
- ❌ DROP TABLE / DELETE 也能跑(没拦截)
- ❌ 用户问"GMV" LLM 不知道是哪个字段

### 关键产出
- 项目雏形 + 7 张表 schema 灌入 MySQL

---

## 阶段 1:补安全(2026-07-05 ~ 07-09)

### 触发
- 7-04 客户问"GMV 多少",LLM 写出 `DROP TABLE fact_order` 然后报错
- 意识到安全是第一优先级

### 关键决策

| 决策 | 当时为什么这么做 | 后来怎么演进 |
|------|----------------|------------|
| 3 层防火墙(关键字 + 白名单 + 注入正则) | 当时认为黑名单够用 | 演进到动态白名单(从 MySQL 读) |
| 硬编码 5 张表白名单 | MVP 阶段先跑通 | 演进到 `meta_mysql_repository.list_tables()` |
| MySQL 账号只读兜底 | 即使代码层漏了,数据库也救不回来 | 一直保留 |

### 关键产出
- `app/core/sql_safety.py` (3 层防火墙)
- `app/core/sql_safety.py` 单元测试(关键字/白名单/注入/防误杀 4 维度)
- `docs/notes/SQL安全设计决策-Grill记录.md`
- `docs/design-decisions/01-sql-safety.md`

### 阶段指标
- SQL 错率 6.5% → 2%
- 危险 SQL 拦截率 100%

---

## 阶段 2:加 RAG(2026-07-10 ~ 07-14)

### 触发
- 安全解决后,问题变成"LLM 不知道表结构"
- 单关键词召回命中率 < 50%

### 关键决策

| 决策 | 为什么 |
|------|--------|
| Qdrant 向量 + ES 全文 + Qdrant 指标 三路召回 | 单一召回不够:向量召回"销售额 ≈ order_amount"准但"华东/华南"混;全文召回"华东"准但"GMV"找不到 |
| 字段名/枚举值/指标分 3 个 Qdrant collection | 不同语义空间不能混索引 |
| `asyncio.gather + return_exceptions=True` 并行 | 单关键词挂了不影响其他 |
| jieba 自定义词典(18 词) | 防止 GMV/SKU 被切碎 |
| LLM 角色压缩:让 LLM 只输出 JSON,SQL 模板渲染 | 让 LLM 干确定性工作(写 SQL 语法)会引入格式不一致 |
| Query 拆分:`state["query"]` 始终原句,`time_range` 单独存 | 时间字符串污染 jieba 切词 |

### 关键产出
- 7 节点 RAG 链路(classify_intent / extract_keywords / 3 路召回 / merge / filter / generate_intent / generate_sql)
- `app/services/sql_template.py` (jinja2 渲染)
- `prompts/generate_intent.prompt`(LLM 角色压缩)
- `app/agent/nodes/_recall_helpers.py`(并行召回 helper)
- `conf/jieba_userdict.txt`(18 词业务词典)

### 阶段指标
- 召回命中率 < 50% → 78%
- 端到端 SQL 错率 2% → 1.5%
- 单 query 端到端延迟 ~5s

---

## 阶段 3:Multi-Agent(2026-07-15 ~ 07-17)

### 触发
- 复杂 query(多 sub 拆分)单 agent 走完整链路太长
- 反思能力缺失,错答案要等用户反馈

### 关键决策

| 决策 | 为什么 |
|------|--------|
| Planner 拆 sub → Send API 并行 → Aggregator 合并 → Reviewer 评分 | 工业级 multi-agent 范式 |
| `MAX_REVIEW_LOOP=2` 硬编码 | 不限反思轮数会被 LLM 滥用,延迟爆炸 |
| `cached_pre_state` 复用上次前置结果 | 反思 retry 不重跑 16s 共享前置 |
| **opt-in 模式**:`use_multi_agent=true` 才走新链路 | 老链路是稳定的 13 节点,改坏了影响生产 |
| 反思回路只在 multi-agent 链路,老 graph 仍用单次 correct_sql | 渐进式迁移,向后兼容 |

### 关键产出
- `app/agent/supervisor_graph.py` (multi-agent 顶层图)
- `app/agent/nodes/{planner,aggregator,reviewer}_node.py`
- 21 节点(老 17 + supervisor 4)

### 阶段指标
- 多 sub 复杂 query 延迟 ~30s → ~25s
- 反思回路命中率:未统计(已知 TODO)
- 端到端 SQL 错率 1.5% → 0.8%(sub 拆分后,每 sub 错率低)

## 阶段 4:全面治理(2026-07-20 ~ 07-22)

### 触发
- 7-19 客户反馈"昨天那个 SQL 不对,复现不了"
- 反思回路命中率没统计,无法调阈值
- LLM 调用全靠日志,没 metric
- prompt 没留痕,无法复现当时 LLM 收到什么

### 关键决策

| 决策 | 为什么 |
|------|--------|
| Memory 三层(Redis 短期 + MySQL 归档 + LangSmith trace) | 解决"复现当时 LLM 收到什么"问题 |
| Eval 三层(unit + smoke + eval_e2e + LLM-as-judge) | 解决"端到端 0.5% 错率真实吗"问题 |
| 数据飞轮(失败案例 → 模式库 → 召回) | 失败案例不要丢,变成下一次召回的素材 |
| LangSmith 可观测性 | 看每节点的 prompt + token + 耗时 |
| 全面安全审计 + 性能优化 + 配置治理 | 7-22 一次性把累积的 24 项小优化做完 |
| `correct_sql` 加 `_is_sql_like` 兜底 | 防止 LLM 输出中文被塞进 sql 字段(7-17 bug 修复) |

### 关键产出
- `app/services/pattern_bank_service.py` (350 行) - SQL 模式库
- `app/services/user_profile_service.py` (216 行) - 用户画像
- `app/services/session_summarizer.py` (150 行) - session 摘要
- `app/services/bad_case_collector.py` (137 行) - 失败案例
- `app/services/memory_decay_service.py` (130 行) - 记忆衰减
- `app/agent/llm_metrics.py` (85 行) - LLM 指标
- `app/core/ttl_cache.py` / `app/core/session.py`
- 4 个 entities + 4 个 models + 4 个 mappers
- `app/scripts/build_pattern_bank.py` / `init_upgrade_tables.py`
- `docs/upgrade-notes/2026-07-22-memory-eval-flywheel.md`

### 阶段指标
- 端到端 SQL 错率 0.8% → < 0.5%(目标)
- prompt 复现能力:0 → 100%(LangSmith trace)
- 失败案例可被召回:0 → 100%(pattern_bank)

## 关键经验(写给未来的自己)

1. **不让 LLM 直接写 SQL**——LLM 干语义层(JSON),代码干确定性工作(模板渲染)
2. **白名单比黑名单更安全**——只允许这 5 张,其他一律不查
3. **不要硬编码"魔法数字"**——`MAX_REVIEW_LOOP=2` / `top_k=20` / 反思阈值 0.7 都要标"经验值",有观测计划
4. **失败案例不要丢**——它就是下一次召回的素材(pattern_bank)
5. **prompt 留痕必做**——用户问"昨天那个 SQL 不对"时,没有 trace 等于失忆
6. **多 agent 反思限上限**——不限反思轮数会被 LLM 滥用
7. **演进三阶段平滑迁移**——WriteMode 阶段 0/1/2,任何阶段出问题可秒回滚
8. **架构层隔离 > 代码层校验**——让 LLM 不写 SQL 才是真安全,SQL 防火墙是兜底
