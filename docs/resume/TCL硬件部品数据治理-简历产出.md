## 一、项目定位

**项目名**　TCL 硬件部品主数据治理,PLM 系统的 ETL 清洗与质量监控闭环

**一句话概括**　对接 PLM,基于 Hive 搭通讯部品主数据清洗模块,76 列字段按 8 条业务规则自动洗,落库到统一新主数据平台;做了"监控 → 清洗 → 再监控"闭环,单批 500 条清洗从 1.5h 压到 10min(9 倍),质量检查从 1h 压到 1min(60 倍),两个 skill 沉淀 + 每批次自动出 HTML/Markdown 报告。

**技术栈**　Python / Hive / PLM 业务系统对接 / ETL 半自动化 / 数据质量监控 / HTML 报告生成 / T 信(企业 IM)告警 / DQC 报告

**需求背景**　硬件部品的主数据散在 PLM 里,操作选项、操作意见、是否修改、ECORating、BU、事业部、环保要求、优选等级这些字段加一起 76 列,人工按业务规范逐条核对,单批 500 条要 1.5 小时,质量检查再 1 小时。一天能处理的批次很有限,经常积压到下游业务方抱怨"数据不准"。

新人接手时没有工程模板,业务规则散在飞书文档里,做两遍才能稳定。这是典型的"业务规则明确 + 数据量上来 + 缺工程化"场景,值得做自动化闭环。

我要做的就是把业务规则固化成可复用 skill,再串成"监控 → 清洗 → 再监控"闭环,让新人也能一个人十分钟把一批准生产数据洗成可用主数据。

## 二、核心亮点(4 条,STAR 法则)

### 亮点 1 · 清洗执行 skill:把 8 条业务规则固化为自动化 ETL

**S(情境)**　硬件部品主数据 76 列字段里有 8 个关键字段(操作选项/操作意见/是否修改/ECORating/BU/事业部/环保要求/优选等级)脏数据率高,但每条脏数据背后都有明确的业务规则(枚举值白名单/格式正则/必填约束)。人工核对时,新人不熟业务规则容易漏;老人一天能处理 2-3 批 500 条,效率天花板明显。

**T(任务)**　把 8 条业务规则从"飞书文档 + 老人经验"里抽出来,固化成新人也能跑的自动化流程,让人工从"逐条核对"解放到"看异常分类处理"。

**A(行动)**　做了 `part-data-cleaning-skill`,核心是程序化业务规则:
- 8 条规则全部编码进 skill 配置,不靠人脑记忆
- 输入:从 PLM 抽出的原始主数据批次(单批 500 条)
- 处理:8 个字段各跑对应规则(枚举白名单/格式正则/必填/跨字段联动)
- 输出:清洗后合规主数据 + 异常明细(便于人工补单)
- 落库:同步到统一新主数据平台

**R(成果)**　单批 500 条从人工 1.5h 压到 10min,9 倍提速。新人按 skill 文档就能上手,不再依赖"老人带";异常明细让人工只需要补单,不用从头看。

---

### 亮点 2 · 质量监控 skill:4 类异常 + 分级告警,60 倍提速

**S**　清洗完的数据要进新主数据平台给业务方用,但清洗后不一定合规。清洗规则有遗漏、新规则没及时更新、跨字段一致性问题会在下游使用时才暴露。原来的做法是人工抽样,500 条样本要 1h 才能扫完,等发现问题时数据已经下发到业务线,回滚成本高。

**T**　把质量检查从抽样变成全量 + 自动化 + 分级告警,让问题在批次内就暴露,流不到下游。

**A**　做了 `master-data-quality-monitor`,核心是全量扫描 + 分级告警:
- 8 条扫描规则覆盖 4 类异常:空值 / 枚举越界 / 格式错 / 跨字段不一致
- 结果按严重程度分级,HIGH 推 T 信(实时触达负责人)/ MEDIUM+LOW 进 DQC 报告(批量汇总)
- 每批次扫描完立即出结果,不积压
- 配套 DQC 报告:HTML + Markdown 双格式,含 4 张质量概览卡片、异常分布表、问题分类占比、修复建议

**R**　每批次质量检查从 1h 压到 1min,60 倍提速。HIGH 异常通过 T 信实时推,负责人不用等日报;MEDIUM+LOW 进 DQC 报告批量处理,问题定位有"问题分类占比"图表辅助,不再靠人肉翻数据。

---

### 亮点 3 · "监控 → 清洗 → 再监控"自动化闭环

**S**　两个 skill 单独跑都没问题,但组合起来有个隐患:清洗规则可能漏掉新出现的脏数据模式,一次扫描就过会让问题累积到下游。手工"清洗完再扫一遍"成本太高,没人愿意做。

**T**　设计自动化闭环,让"监控 → 清洗 → 再监控"成为标准流程,确保每一批主数据都是经过验证合规的。

**A**　核心是串行编排 + 异常分类驱动:
1. 第一轮监控。`master-data-quality-monitor` 跑 4 类异常扫描
2. 清洗。`part-data-cleaning-skill` 按异常分类做定向清洗
3. 第二轮监控。再扫一遍,确认异常清零或降到阈值以下
4. 不达标则阻断。剩余异常超阈值,该批次不落库到新主数据平台,要求人工补单

**R**　闭环协作消除了"清洗完直接落库"的隐患。两个 skill 不是孤岛,而是同一个治理流程的"前置 + 后置";新人按 skill + 闭环文档就能跑出经过验证的合规主数据,不再靠经验。

---

### 亮点 4 · DQC 报告自动化 + 沉淀工程模板

**S**　质量监控结果散在脚本输出里,业务方和 leader 看不到全局。新人想了解"最近这批主数据质量如何",得自己跑脚本、翻日志、做统计,光搞清楚状况就要 30 分钟;leader 关注的"问题集中在哪类字段、修复优先级如何"完全没有可视化。

**T**　每批次监控结果自动出可视化报告 + 摘要,业务方和 leader 一眼能看懂,问题定位 + 修复建议直接给到。

**A**
- HTML 报告:4 张概览卡片(总览/严重度分布/异常类型占比/字段热力图)+ 异常分布表
- Markdown 摘要:精简版,贴飞书/邮件给非技术 stakeholder
- 修复建议:基于异常分类自动给"哪些字段、什么规则、怎么改"建议
- 工程模板:把"清洗 + 监控"完整链路封装成模板,后续其他部品(整机/外设)接入只需改配置

**R**　问题定位时间从 30min 压到 1min。Leader 不再问"这批怎么样",主动收到 DQC 报告;模板化让后续部品接入成本降到"改 yaml 不改代码"。

## 三、面试深挖备用

### Q1:为什么把业务规则做成 skill 而不是脚本?

业务规则会变,环保要求新规、事业部重组都可能改。脚本硬编码改起来要动代码;做成 skill 是配置 + 规则引擎的模式,新增/修改规则只动 yaml,核心代码一行不碰。Skill 还是个可复用单元,后续其他部品(整机/外设)接入直接复用,避免每个品类都重写一遍。

### Q2:清洗规则怎么定的?8 条够不够?

8 条是当前通讯部品跑下来的最小可用集,覆盖 4 类典型脏数据:空值(必填字段缺失)/ 枚举越界(事业部/BU 不在白名单)/ 格式错(ECORating 必须是 X/Y/Z 之一)/ 跨字段不一致(环保要求"是"但未填具体材料)。后续会按 DQC 报告的"问题分类占比"动态增补,报告驱动规则迭代。

### Q3:HIGH 告警为什么用 T 信而不是邮件/短信?

T 信是企业 IM,HIGH 异常要负责人立即看到并响应,等不及邮件;短信成本高又不接企业身份;T 信通过群机器人 webhook 推送,接 DQC 报告链接,1 秒触达 + 1 跳查看详情,延迟最低。

### Q4:为什么"监控 → 清洗 → 再监控"要跑两轮?

第一轮发现问题,清洗修复,第二轮验证修复。只跑一轮相当于"自己说自己好",可信度没保障;两轮监控异常清零才落库,这是对下游业务方的质量承诺。如果第二轮仍有 HIGH 异常,阻断落库,不是"先发出去再说"。

### Q5:为什么不直接用开源数据治理工具?

预算上,商用 ETL 工具 license 贵,公司预算有限。规模上,通讯部品单批 500 条,远没到大数据治理工具的适用阈值。维护上,用脚本/skill 团队能直接维护,商用工具出问题要厂商支持,响应慢。够用就好,不追大而全。

### Q6:DQC 报告怎么保证非技术 stakeholder 看得懂?

设计原则是"3 秒看懂 + 1 分钟定位":4 张卡片给总览(总条数/异常率/HIGH 占比/字段健康度),异常分布表给定位(按字段 × 异常类型聚合),修复建议给行动(自动生成,不用 stakeholder 问"那怎么改")。业务方/leader 不需要懂技术细节,看图 + 文字就能做决策。

## 六、面试话术要点

**30 秒自我介绍**

TCL 实习我做了硬件部品主数据治理的自动化闭环。原来单批 500 条主数据,人工清洗 1.5h + 质量检查 1h,新人没模板根本跑不动。我把 8 条业务规则固化成 `part-data-cleaning-skill` 清洗 skill,9 倍提速;再做 `master-data-quality-monitor` 监控 skill,8 条规则扫 4 类异常,60 倍提速;最后把两个 skill 串成"监控 → 清洗 → 再监控"闭环,异常清零才落库,保证下游拿到的都是验证过的合规主数据。配套每批次自动出 DQC 报告,leader 不用问就能看到问题分布。

**深挖引导**

- 面试官问"为什么做这个",引到业务痛点(76 列/500 条/1.5h 人工)→ 规则明确但缺工程化 → 自动化闭环
- 面试官问"skill 怎么设计",引到配置 + 规则引擎模式,改规则不动代码
- 面试官问"监控怎么发现新问题",引到 DQC 报告驱动规则迭代(问题分类占比 → 补规则)
- 面试官问"为什么用 T 信",引到实时性 + 企业身份 + 群机器人 webhook,延迟最低
- 面试官问"为什么跑两轮监控",引到"自己说自己好"没保障,第二轮是质量承诺;HIGH 异常阻断落库是 fail-closed
- 面试官问"为什么不用商用 ETL 工具",引到预算 + 数据规模 + 维护成本,够用就好不追大而全

**避坑提醒**

- 别说"独立完成整个 ETL 平台",准确是做了两个 skill + 闭环设计,数据中台和 PLM 是公司现成的
- 别说"实现了 AI 数据治理",这是业务规则固化的自动化,不是 AI;用 skill/规则引擎,不堆 AI buzzword
- 量化数字要给单批 500 条 + 1.5h → 10min / 1h → 1min 这种有证据的口径,不要拍脑袋写"提升 100 倍"
- 闭环讲清楚两轮监控各干什么,第一轮发现,第二轮验证,不是"扫两遍相同的事"
- DQC 报告讲"3 秒看懂 + 1 分钟定位"的设计目标,别说"做了 dashboard"这种空话

## 七、项目意义总结

1. **从手工核对到 skill 自动化**　业务规则明确但散落各处,固化成可复用 skill 后,新人按文档就能上手,不再依赖"老人带"。这是工程化最朴素的胜利。
2. **从单点工具到闭环流程**　`part-data-cleaning-skill` 和 `master-data-quality-monitor` 单独用都有价值,串成"监控 → 清洗 → 再监控"才是给业务方的质量承诺;HIGH 阻断落库是 fail-closed 的底线。
3. **从脚本输出到可视化报告**　DQC 报告让非技术 stakeholder 也能看懂,leader 不再问"这批怎么样",主动收到。沟通成本降低,比技术本身更有价值。
4. **从一次性项目到模板沉淀**　把"清洗 + 监控"链路封装成模板,后续其他部品接入改 yaml 不改代码,资产复用才是数据治理能持续做下去的关键。
5. **从效率工具到质量闭环**　9 倍 / 60 倍提速只是表面,真正的价值是让每一批主数据都可追溯、可验证、可阻断。效率是结果,质量是目的。
