## 1. Flink 核心架构(必答)

```
┌────────────────────────────────────────────┐
│  Client(提交 Job)                            │
└──────────────┬─────────────────────────────┘
               ↓
┌──────────────▼─────────────────────────────┐
│  JobManager(主节点)                          │
│  - Dispatcher:接收 Job 提交                  │
│  - ResourceManager:slot 资源调度              │
│  - JobMaster:单个 Job 的主控                  │
└──────┬───────────────────┬─────────────────┘
       │                   │
       ↓                   ↓
┌──────────────┐    ┌──────────────┐
│ TaskManager  │    │ TaskManager  │
│  - n 个 Slot │    │  - n 个 Slot │
│  - 跑 Task   │    │  - 跑 Task   │
└──────────────┘    └──────────────┘
```

**关键术语**:
- **Slot**:TaskManager 的资源隔离单元(内存 + CPU),同一个 Job 的不同 Task 可以共享 Slot(允许 pipeline 共享,默认)
- **并行度(Parallelism)**:一个算子被拆成几份并行跑
- **算子链(Operator Chain)**:多个算子能链在一起跑在同一个 Slot 里,减少线程切换

## 2. Flink vs Spark Streaming 一句话对比(藤子速考 5 题里唯一答不上来的,这次必须背)

| | Flink | Spark Streaming |
|---|-------|-----------------|
| 处理模型 | **真流**(每条事件驱动) | **微批**(攒一批再算) |
| 延迟 | 毫秒级 | 秒级 |
| 时间语义 | 事件时间优先 | 处理时间为主 |
| 状态管理 | 内置完整 State | 需要外部存储 |

**面试话术**:"Flink 是真流处理,每个事件触发一次计算,毫秒级延迟;Spark Streaming 是微批,把流切成小批,本质还是批处理,所以秒级延迟。我们项目选 Flink 是因为业务要实时反作弊,毫秒级延迟是硬指标。"

## 3. 时间语义 + Watermark(高频)

**3 种时间**:
- **事件时间(Event Time)**:事件真实发生的时间(写在数据里)→ 真实业务用这个
- **处理时间(Processing Time)**:算子处理到这条数据的时间(机器时间)→ 简单但不准
- **摄入时间(Ingestion Time)**:数据进入 Flink 的时间(中间值)→ 几乎不用

**Watermark**:
- **是什么**:一种特殊的时间戳,**标记"事件时间已经推进到 T,不会再有 < T 的数据"**
- **作用**:配合 Event Time 窗口,**解决乱序问题**
- **核心比喻(藤子亲测有效)**:Watermark = "等朋友" —— 你约朋友 7 点到,你 6:50 到,你愿意等到 7:10(给 10 分钟迟到容忍);Watermark 就是这个"等多久"的边界

**Watermark 公式**:`Watermark = 当前最大事件时间 - 最大乱序度`

## 4. 窗口机制(必答)

| 类型 | 描述 | 例子 |
|------|------|------|
| **滚动窗口(Tumbling)** | 固定大小,不重叠 | 每分钟统计一次订单数 |
| **滑动窗口(Sliding)** | 固定大小,可重叠 | 每 5 分钟统计过去 10 分钟 |
| **会话窗口(Session)** | 动态大小,按活动间隔 | 用户行为间隔 30 分钟算一次会话 |
| **全局窗口(Global)** | 所有数据一个窗口 | 配合 Trigger 手动触发 |

**关键 API**(面试常写):
```python
stream.key_by(...)
      .window(TumblingEventTimeWindows.of(Time.minutes(5)))
      .allowedLateness(Time.minutes(1))   # 迟到容忍
      .aggregate(MyAggregateFunction())
```

## 5. 状态管理 + Checkpoint(必答)

**State 类型**:
- **Keyed State**:跟 key 绑定的状态(每个 key 一份)→ ValueState / ListState / MapState
- **Operator State**:跟算子实例绑定(每个并行度一份)→ Kafka offset 这种

**StateBackend(状态后端)**:
- **HashMapStateBackend**:内存,快,小状态用
- **RocksDBStateBackend**:磁盘,大状态用,增量 checkpoint 友好

**Checkpoint(检查点)**:
- **是什么**:周期性把分布式状态快照存到外部存储(HDFS/S3)
- **算法**:Chandy-Lamport 分布式快照(异步 barrier 对齐)
- **配置**:`env.enableCheckpointing(60000)` 1 分钟一次

**重启策略**:
- **固定延迟**:失败后等 N 秒重启,最多 M 次
- **失败率**:10 分钟内失败 N 次就放弃
- **无重启**(默认):生产环境几乎不用

## 6. 反压机制(进阶)

- **是什么**:下游处理慢,信号传给上游,上游自动降速
- **早期**:TCP-based 反压(网络 buffer 满)→ 延迟高
- **现在**:Credit-based 反压(每个 Task 给上游发"credit"额度)→ 精确
- **面试话术**:"Flink 的反压是从下游往上游传,每个下游告诉上游我还能吃多少,上游根据这个调整发送速率。我们生产中靠这个机制保证 Kafka 消费不会爆掉内存。"

## 7. Flink vs Spark 选型(架构题)

| 场景 | 选 Flink | 选 Spark |
|------|----------|----------|
| 实时反作弊 / 风控 | ✅ 毫秒级 | ❌ 延迟太高 |
| 实时数仓(秒级) | ✅ | ✅(Flink 也行) |
| 离线数仓 ETL | 杀鸡用牛刀 | ✅ 成熟稳定 |
| 机器学习(批) | 一般 | ✅ MLlib 生态 |
| SQL 标准化 | Flink SQL 越来越强 | Spark SQL 成熟 |

**面试话术**:"如果业务是'实时告警 / 风控',必须 Flink(毫秒级);如果是'T+1 报表 / 离线数仓',Spark 更划算(生态成熟、SQL 标准化)。我们项目双跑,离线用 Spark,实时用 Flink。"
