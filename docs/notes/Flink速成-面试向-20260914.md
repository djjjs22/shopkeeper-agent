## 1. Flink 是什么（一句话定位）

**Flink = 分布式流处理框架**。

大白话：
- Spark 是"批处理为主，流是微批"（把流切成小批跑）
- Flink 是"流处理为主，批是流的特殊情况"（每条数据来了就处理）

**核心优势**：低延迟（毫秒级）、Exactly-Once 精确一次语义、事件时间处理。

面试话术：
> "Flink 是**以流为核心的分布式计算引擎**，主打低延迟和高一致性。相比 Spark Streaming 的微批，Flink 是真正的逐条处理，延迟能到毫秒级。"

---

## 2. 3 个核心概念（必背）

| 概念 | 大白话 | 面试话术 |
|------|--------|----------|
| **Stream** | 一条不断流过来的数据 | 数据流，分有界（批）和无界（流） |
| **Transformation** | 对数据的处理动作 | map / filter / keyBy / window / aggregate |
| **Sink** | 数据处理完写到哪里 | 写 Kafka / MySQL / Redis / HDFS |

**一个作业 = Source（读）+ Transformation（算）+ Sink（写）**

---

## 3. 流和批的区别（高频追问）

| 维度 | 流（Streaming） | 批（Batch） |
|------|----------------|------------|
| 数据 | 无界（一直来） | 有界（一次跑完） |
| 延迟 | 毫秒-秒 | 分钟-小时 |
| 引擎 | Flink / Kafka Streams | MapReduce / Spark / Hive |
| 典型场景 | 实时看板、监控告警 | T+1 报表、离线分析 |

**Flink 的优雅之处**：**流和批用同一套 API**。一个流作业加个 `bounded` 标记就是批。

## 4. 事件时间 vs 处理时间（必考）

这是 Flink 面试**最高频**的题，没有之一。

| 类型 | 含义 | 用法 |
|------|------|------|
| **事件时间（Event Time）** | 数据**产生时**的时间（业务时间） | 真实业务发生时间 |
| **处理时间（Processing Time）** | 数据**被处理**时的时间（Flink 机器时间） | 算延迟等运维场景 |
| **摄入时间（Ingestion Time）** | 数据**进入 Flink** 的时间 | 介于两者之间 |

**为什么要分？** 因为数据会乱序。

**举例**：
```
19:55 用户点了"提交订单"（事件时间）
      ↓ 网络延迟
20:03 Flink 收到这条数据（处理时间）
```

如果按处理时间算，这笔订单算到了 20:03 那分钟——**业务上不对**。

**面试话术（必背）**：
> "**生产里必须用事件时间**，处理时间会导致乱序数据归错窗口。比如日志回补、用户离线点击都会乱序，处理时间算出来的指标跟业务对不上。"

## 5. Watermark 水位线（必考）

**问题**：用事件时间，但数据有乱序，**窗口什么时候才触发计算？** 你不能无限等。

**解法**：Watermark = "**我等到了这个时间点，之前的都该到了**"。

大白话：
> 你去电影院等朋友，约定"我等到 7 点，7 点还没来我就自己进去了"。**Watermark 就是这个 7 点**——一个时间戳，Flink 认为**比这个时间戳早的数据都到齐了**。

**机制**：
- Watermark 周期生成（默认 200ms 一次）
- 当 Watermark ≥ 窗口结束时间，窗口才触发计算
- Watermark 滞后时间 = `当前最大事件时间 - 允许乱序度`

**举例**：
```
窗口：[10:00, 10:01)
Watermark = 10:01:00 → 窗口 [10:00, 10:01) 触发

乱序容忍 = 5 秒：
Watermark = 10:01:00 - 5s = 10:00:55 → 10:00:55 之前的数据都到齐了
```

**面试话术（必背）**：
> "Watermark 是**事件时间下的进度标记**，告诉 Flink '比这个时间早的数据都到齐了，可以关闭窗口触发计算了'。**乱序容忍度设小了 → 数据丢失**；**设大了 → 延迟增加**。生产一般设 5-10 秒，要根据业务乱序程度调。"

## 6. Window 窗口（必考）

Flink 把无限流切成一块块计算。**窗口 = 有限的数据块**。

### 6.1 4 种窗口类型

| 类型 | 含义 | 适用场景 |
|------|------|----------|
| **滚动窗口（Tumbling）** | 固定大小，**不重叠** | 每分钟 UV、每分钟订单数 |
| **滑动窗口（Sliding）** | 固定大小，**有重叠** | 最近 5 分钟的 UV（每 1 分钟算一次） |
| **会话窗口（Session）** | 一段时间没活动就关闭 | 用户访问会话（30 分钟没动作算结束） |
| **全局窗口（Global）** | 所有数据一个窗口 | 配合 Trigger 自定义触发 |

### 6.2 大白话举例

> 滚动窗口 = 每天的 24 小时整点切片（00:00、01:00...）
> 滑动窗口 = 最近 1 小时的数据，但每 5 分钟算一次（00:00、00:05、00:10...）

**面试话术**：
> "实时 UV 用**滚动窗口 + 去重**（按 userId keyBy + 布隆过滤器）。**滑动窗口**算'最近 5 分钟在线用户数'这种会重复算同一个用户，要去重。"

## 7. State 状态后端（必考）

### 7.1 什么是 State

**State = Flink 算子维护的"记忆"**。

比如：
- 算 UV 要记"这个 userId 出现过没" → 状态
- 算 5 分钟求和要记"过去 5 分钟的值" → 状态
- 算最近 10 次点击的均值要记"前 9 次" → 状态

**没有状态 = 每条数据都孤立的 = 啥聚合都做不了**。

### 7.2 状态后端 2 种

| 类型 | 存在哪 | 适用 |
|------|--------|------|
| **MemoryStateBackend** | TaskManager 内存 | 本地测试、小状态（< 1GB） |
| **RocksDBStateBackend** | 本地 SSD + 内存缓存 | **生产首选**，大状态（GB-TB 级别） |

**面试话术（必背）**：
> "生产用 **RocksDBStateBackend**。原因：状态大（UV 去重要存几亿 userId），内存放不下；RocksDB 把状态序列化到本地 SSD，**内存里只放热点数据**，重启可恢复。代价是状态读写有序列化开销，比纯内存慢 5-10 倍。"

## 8. Checkpoint 容错（必考）

**问题**：Flink 任务跑一半挂了，**算到一半的窗口数据会不会丢？**

**解法**：Checkpoint = **定期给状态拍快照**。

### 8.1 工作原理

```
正常跑
  ↓ 每 1 分钟（或 X 秒）
触发 Checkpoint：
  - 暂停处理（或者用 Chandy-Lamport 异步拍）
  - 把所有 State 写入 HDFS/S3
  - 把 Kafka offset 一起存
  ↓
Checkpoint 完成，继续处理

如果挂了：
  - 重启
  - 读最近 Checkpoint
  - Kafka 从 offset 重放
  - State 恢复 → 继续处理
```

### 8.2 Exactly-Once 怎么实现

**两阶段提交（2PC）** + Checkpoint：
- Flink 算子收到 Checkpoint barrier → 暂停输出
- 算子把结果"预提交"到外部存储（Kafka/HDFS）
- 所有算子都预提交成功 → Checkpoint 完成
- 真正提交；否则回滚

**面试话术（必背）**：
> "Flink 通过 **Checkpoint + 2PC** 实现 Exactly-Once。Checkpoint 存状态和 Kafka offset，外部 Sink 走两阶段提交。代价是延迟略高。**生产里 Exactly-Once 不是免费的**——Sink 必须支持事务（Kafka 0.11+ / MySQL / HDFS 都支持），不支持的 Sink 只能做到 At-Least-Once。"

## 9. 反压机制（高频追问）

### 9.1 什么是反压

**反压 = 下游处理慢，上游被"憋住"**。

举例：
- Kafka → Flink → Redis
- Redis 写入突然变慢（比如大 Key）
- Flink 算完等 Redis 返回，数据堆在内存
- Flink 算子变慢 → Kafka 那侧反压

### 9.2 Flink 怎么解决（Credit-based）

**老版本（Spark 也有）**：TCP 反压，task 满了就 stop/ack 一下游，**粗暴**。

**新版本（flink 1.5+）**：**Credit-based 反压**。

大白话：
> 就像高速公路 ETC——下游告诉上游"我现在还能接收多少"，上游按这个数量发。**不堵车，不空跑**。

具体机制：
- Flink 把数据切成**子分区（subpartition）**
- 下游给每个上游 channel 发"我还有 N 个 buffer"（Credit）
- 上游按 Credit 数量发数据
- 下游满了 → Credit 变 0 → 上游自然停

**面试话术（必背）**：
> "Flink 1.5+ 用 **Credit-based 反压**——下游给上游发 buffer 信用额度，上游按额度发数据。**好处是细粒度、跨 task 也能反压**，不会出现 Spark 那种整批次卡死。生产排查反压看 Flink Web UI 的 backpressure 指标，定位到具体算子后**查下游慢在哪**（一般是外部 Sink 慢）。"

## 10. 架构：JobManager / TaskManager

```
┌─────────────────────────────────────┐
│          JobManager (Master)         │
│  - 调度 Task                         │
│  - 协调 Checkpoint                    │
│  - 故障恢复                          │
└─────────────────────────────────────┘
              ↓ 调度
┌──────────┬──────────┬──────────┐
│TaskManager│TaskManager│TaskManager│ (Worker)
│  Task    │  Task    │  Task    │  跑具体的算子
│  Subtask │  Subtask │  Subtask │
└──────────┴──────────┴──────────┘
```

| 组件 | 职责 | 类比 |
|------|------|------|
| **JobManager** | 调度、容错、协调 | 公司 CEO |
| **TaskManager** | 跑具体的算子任务 | 干活的员工 |
| **Task Slot** | TaskManager 内的资源隔离单元 | 员工的工位 |

**关键概念**：
- 一个 Flink 作业 = 一个 JobGraph
- 每个算子并行度 = 1 个 subtask
- N 个 TaskManager × 每个 M 个 slot = 总并行度

## 11. 真实项目里怎么写 Flink 作业

### 11.1 核心 API（DataStream）

```java
DataStream<String> source = env
    .addSource(new FlinkKafkaConsumer<>("topic", new SimpleStringSchema(), props))
    .name("kafka-source");

DataStream<Bean> parsed = source
    .map(json -> JSON.parseObject(json, Bean.class))
    .name("parse");

DataStream<Bean> keyed = parsed
    .keyBy(Bean::getUserId);

DataStream<Bean> windowed = keyed
    .window(TumblingEventTimeWindows.of(Time.minutes(1)))
    .aggregate(new MyAggregateFunction());

windowed
    .addSink(new RedisSink<>(...))
    .name("redis-sink");
```

### 11.2 SQL API（更简单）

```sql
SELECT
  TUMBLE_START(event_time, INTERVAL '1' MINUTE) as window_start,
  COUNT(DISTINCT user_id) as uv
FROM user_click_log
GROUP BY TUMBLE(event_time, INTERVAL '1' MINUTE);
```

**面试话术**：
> "复杂逻辑用 **DataStream API**（更灵活），简单聚合用 **Flink SQL**（更易维护）。生产里 80% 的 UV/PV 统计走 SQL，剩下 20% 复杂业务（多流 join、状态机）才用 DataStream。"

## 12. 高频面试题 10 道（带答案）

### Q1：Flink 和 Spark Streaming 区别？

> Flink 是**真流**（逐条处理，毫秒延迟），Spark Streaming 是**微批**（按时间切片跑，秒级延迟）。Flink 在事件时间、状态管理、Exactly-Once 上更成熟。

### Q2：什么是事件时间？为什么必须用？

> 业务真实发生的时间。处理时间会因为网络延迟、乱序把数据归错窗口。**生产必须用事件时间 + Watermark**。

### Q3：Watermark 是什么？怎么设？

> Watermark 是"事件时间进度标记"，表示"比这个时间早的数据都到齐了"。**设小 → 数据丢失；设大 → 延迟增加**。生产按业务乱序度（一般 5-10 秒）调。

### Q4：状态后端选哪个？为什么？

> 生产用 **RocksDB**。状态大（GB-TB），内存放不下；RocksDB 序列化到 SSD + 内存缓存热点。**重启可恢复，状态不丢**。

### Q5：Exactly-Once 怎么实现？有限制吗？

> **Checkpoint + 两阶段提交**。限制：Sink 必须支持事务（Kafka 0.11+ / MySQL / HDFS）。**不支持的 Sink 只能 At-Least-Once**。

### Q6：反压是什么？怎么排查？

> 下游慢导致上游积压。Flink 1.5+ 用 **Credit-based 反压**。排查看 Web UI 的 backpressure 指标，**找到具体算子**后查下游（一般是外部 Sink 慢）。

### Q7：滑动窗口和滚动窗口的区别？什么时候用？

> 滚动 = 不重叠，**周期性指标**（每分钟 UV）。滑动 = 有重叠，**连续指标**（最近 5 分钟在线用户，每 1 分钟更新一次）。

### Q8：Flink 任务挂了怎么办？

> 从**最近 Checkpoint 恢复** + Kafka offset 重放。JobManager 重启 TaskManager，重新调度 subtask，**状态从 HDFS 加载**。一般 10-30 秒恢复。

### Q9：双 11 流量 10 倍怎么扛？

> ① 提前**扩容 Kafka 分区**（下游消费并行度跟着涨）② **Flink 自适应反压**自动降速不丢数 ③ 关键作业设**独立资源池**，不被其他作业挤占 ④ **限流/降级开关**——非核心指标暂时不跑。

### Q10：Flink CDC 知道吗？

> Flink CDC = 用 Flink 实时捕获数据库 binlog（如 MySQL）。**生产里 MySQL → Kafka → Flink CDC → 实时数仓**是主流方案，替代了传统的 Canal。

## 一句话总结（背下来）

> "Flink 是**以流为核心的分布式计算引擎**，核心优势是**事件时间 + Exactly-Once + 低延迟**。生产里用它做实时数仓、CDC 同步、监控告警。**关键设计点**：状态后端选 RocksDB、Checkpoint + 2PC 保 Exactly-Once、Watermark 控乱序、Credit-based 反压自适应。**最大坑**：Exactly-Once 需要 Sink 支持事务，否则只是 At-Least-Once。"
